[#wasi-wasip3]
== wasip3

The same main serves WASI 0.3: only the build differs, and with b2 it
differs by the toolset alone, `clang-wasip3`. By hand:

* the world exports `wasi:http/handler@0.3.0`, with the `wasi:http` 0.3.0
  WIT in `wit/deps/`, the `wit/deps` directory of the Rust crate `wasip3`
  0.9.0;
* the bindings are generated with `--async 'wasi:http/handler@0.3.0#handle'`
  beside `--rename-world`;
* everything is compiled for `--target=wasm32-wasip3`, the `.c` of the
  bindings with `-pthread`, and the program with `-DWEBCPP_WASI_HTTP_P3`;
* wasmtime serves it with `-S cli,p3 -W component-model-async`.

The world of <<wasi-build-by-hand>> then exports the handler of 0.3.0:

[listing]
----
include::{examples}/by_hand/p3/wit/world.wit[tag=world]
----

and these commands build it, with exceptions on, as webcpp builds every
program for wasip2 and wasip3, and as the commands of wasip2 do
(<<wasi-boost-exceptions>>):

[source,bash]
----
include::{examples}/by_hand/build.sh[tag=p3]
----

The test `by_hand` runs them in its lane on wasip3, and wasmtime serves what
they build with the flags above and no other. With exceptions on, an
exception that escapes the main traps the instance: the handler catches
nothing, and wasmtime 47 answers the client with its own
`500 Internal Server Error` (<<wasi-main-rules>>). Built with
`-fno-exceptions` in place of the exception flags, on the compile and on
the link, the component answers the same; webcpp measured that once, by
hand, on wasip3, and its lanes build both versions with exceptions.

The handler of wasip3 is lifted asynchronously, but it never gives its task
back to the host to wait: it waits for each write inside the task, and always
ends with `EXIT` (<<wasi-invariant-5,guarantee 5>>). On wasip3, context slot
0 of the component model belongs to wasi-libc, and a handler that resumed in
its callback would need it: using it trapped.
