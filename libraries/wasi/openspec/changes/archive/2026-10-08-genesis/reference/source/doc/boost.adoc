[#wasi-boost]
== Building for WASI with Boost

wasi itself needs no Boost, but a component rarely stops at its handler: it
parses JSON, computes, keeps state. webcpp builds every library it holds for
wasm32-wasip2 and wasm32-wasip3, Boost included, and this chapter shows what
its build does for that, so that a project of its own can do the same. Every
listing below is the build's own configuration, included from the file the
build reads, or a program webcpp compiles and runs on both targets on every
build.

Boost.JSON, Boost.System, Boost.Decimal and Boost.MSM build and run on both
targets in webcpp's lanes, as the tests and the examples of its libraries
use them; <<wasi-boost-json>> shows the first in a command and in a
component.

[#wasi-boost-toolsets]
=== The toolsets

The WASI toolsets are b2's `clang`, registered against wasi-sdk 34 under the
versions `wasip2` and `wasip3`, so that `toolset=clang-wasip2` and
`toolset=clang-wasip3` name them. A `user-config.jam` registers them with
these lines, the first two of which name wasi-sdk's directory and give it to
the build, which builds the component of a script with it
(<<wasi-testing-library>>); the CI writes them into the user-config of each
of its WASI lanes, with the directory where it installed wasi-sdk:

[listing]
----
include::{webcpp-root}/tools/ci/wasi-sdk.jam[tag=wasi-sdk]

include::{webcpp-root}/tools/ci/wasi-sdk.jam[tag=wasip2]

include::{webcpp-root}/tools/ci/wasi-sdk.jam[tag=wasip3]
----

Each gives the target to the compilers and to the linker, and makes
archives with wasi-sdk's own `llvm-ar` and `llvm-ranlib`.

wasm32-wasip2 is no system b2 knows. webcpp's Jamroot declares a target
system `wasi` of its own, whose programs end in `.wasm`:

[listing]
----
include::{webcpp-root}/Jamroot[tag=wasi-os,indent=0]
----

It declares it after the toolsets of the `user-config.jam` have loaded, so
that none of the Unix link options that b2 gives the systems it knows, such
as `--start-group` or an rpath, reaches wasi-sdk's linker, which rejects
them. Every target of the two toolsets is then built for that system, and
linked statically, since WASI has no shared libraries:

[listing]
----
include::{webcpp-root}/Jamroot[tag=wasi-target,indent=0]
----

A program built so runs with wasmtime, which b2 starts for a test or an
example given `testing.launcher=wasmtime` on its command line, beside
`toolset=clang-wasip2` or `toolset=clang-wasip3` (<<wasi-testing-targets>>).

[#wasi-boost-exceptions]
=== Exceptions on wasip2 and wasip3

A program may use exceptions on wasip2 and wasip3, as natively: whether it
does is its developer's choice, and webcpp builds every program for both
with them on, encoded as WebAssembly's exception handling:

[listing]
----
include::{webcpp-root}/Jamroot[tag=wasi-exceptions,indent=0]
----

`-fwasm-exceptions` encodes a throw and a catch as WebAssembly instructions,
on the compile and on the link, and `-lunwind` links the runtime that
unwinds the stack. `-mllvm -wasm-use-legacy-eh=false` chooses which
instructions: the Clang of wasi-sdk 34 emits by default the legacy encoding
of the proposal's first version, and wasmtime 47 refuses to run a program
that uses it, saying `legacy_exceptions feature required`. With the flag,
Clang emits the standard encoding, `exnref`, which wasmtime runs, and serves
in a component, with no flag of its own.

A program that uses exceptions needs a host that runs that encoding, which
WebAssembly 3.0 made standard: wasmtime 47 or later, or wasmtime 37 to 46
given `-W exceptions=y`; jco, whose `jco transpile` is given
`--bindgen-enable-wasm-exnref`; or another engine of WebAssembly 3.0.

wasi's handler catches nothing: an exception that escapes the main traps the
instance, and wasmtime 47 answers the client with its own
`500 Internal Server Error` (<<wasi-main-rules>>). A main that may throw
catches what it can answer itself.

A user's build without exceptions, `exception-handling=off`, compiles with
`-fno-exceptions` alone, under which Boost.Config defines
`BOOST_NO_EXCEPTIONS`, and that asks something of the program. Where Boost
would throw, it calls `boost::throw_exception`, which its headers declare
and leave to the program to define: a program built without exceptions that
calls it, as Boost.System's `result` and Boost.JSON do, does not link
without a definition. webcpp's
https://github.com/webcpporg/webcpp/blob/main/tools/throw_exception.cpp[`tools/throw_exception.cpp`]
defines both overloads: each prints what was thrown on the standard error,
and aborts, since a throw in such a build is a defect, never a condition.
webcpp's build links it into every program a user builds with
`exception-handling=off`, on any target. A program built by hand without
exceptions compiles with `-fno-exceptions -DBOOST_NO_EXCEPTIONS`, and
compiles and links that file, or a definition of its own.

So a program that may be built without exceptions asks Boost for errors as
values. The command of <<wasi-boost-json>> parses with an `error_code`,
which a broken text sets, and reads the value with `if_object` and
`if_contains`, which answer a null pointer for what is not there; `as_object`
and `at` would report it by throwing, which in such a build ends the
program.

`<webcpp/wasi/config.hpp>`, which every public header of wasi includes
first, defines `WEBCPP_WASI_NO_EXCEPTIONS` when the build has no exceptions
or when the program defines `WEBCPP_NO_EXCEPTIONS`, which turns off the
exceptions of every webcpp library at once, and a program may define it for
wasi alone, to turn wasi's exceptions off in a build that has them, as
Boost.Asio's `BOOST_ASIO_NO_EXCEPTIONS` does. wasi reads
`WEBCPP_NO_EXCEPTIONS` itself, since it includes nothing of Boost, nor
`<webcpp/config.hpp>`, which includes Boost.Config. wasi raises no exception
of its own, so the macro changes nothing in it: it exists so that a program
can set it for every webcpp library alike. The tests `config`,
`config_developer_defined` and `config_all_off` check the three ways it is
defined, natively and on both targets, and the lint refuses a `throw` in a
public header, even in a template nothing instantiates: an exception goes
through `boost::throw_exception`.

=== Boost.JSON

Boost.JSON is not only headers: its definitions are compiled once in a
program, from the translation unit that includes `<boost/json/src.hpp>`.
webcpp builds that translation unit as the static library
`/webcpp//boost_json`, once for each variant and target, so that the
program's own features, such as `<exception-handling>off`, reach it; a
program links it with `<library>/webcpp//boost_json`, and needs no compiled
Boost library. wasi's two programs of this chapter do so:

[#wasi-boost-unsupported]
=== What does not build

Boost.Asio 1.92 does not compile for wasm32-wasip2 or wasm32-wasip3 with
wasi-sdk 34: wasi-libc defines no `ESHUTDOWN` and no `::pause`, and its
`signal.h` stops with `#error`. It was measured when webcpp's first library,
xactor, was ported: its Asio driver is built natively alone, and xactor
records why in its example Jamfile and on
link:{webcpp-libs}/xactor/{webcpp-page}#xactor-drivers-asio[its page].
